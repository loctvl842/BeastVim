Keymap condition: dev plan

Key.safe_set learns cond. A boolean or a function that returns true/false decides registration at once. A function that returns nothing and calls done(ok) later is a slow check: the key is registered as a toast-only placeholder, then swapped for the real keymap on yes or removed on no, error or timeout. Slow-check bookkeeping lives in a new key/cond.lua. PM spec: docs/pm-specs/key-cond.md.

Context

Problem. KeymapBase cannot say "register only if X". Callers hand-roll an if (e.g. sync_gh_keys in lua/beast/init.lua), and an external-command check either blocks the editor or leaves a dead key in the hint.

Solution. core.safe_set evaluates cond once per call. Slow answers go through key/cond.lua, which owns the pending table, the 10 s timer and the swap/remove. core.set and core.del get small hooks.

Research

Repo search

  • core.lua: KeymapBase has no cond; the skip table (line 280) already filters has/group/once from vim.keymap.set options; safe_set (375) loops modes.
  • core.set records conflicts via resolve_call_site, which finds no user frame when called from an async callback. The swap must reuse the registration-time site or it is reported as a duplicate.
  • Hint and cheatsheet read Key.managed and rebuild on BeastKeysChanged: placeholders and removals show up with no hint change.
  • lsp/attach.lua: Beast.Lsp.KeySpec already declares cond?: string (an LSP method). Type clash, no runtime clash (never forwarded to safe_set).
  • packer/triggers/keys.lua builds options from a fixed list, so cond on a lazy key would be silently dropped.
  • Packer plugin specs already use cond as "false means skip": same name, same meaning.

Decision

Build key/cond.lua on top of existing core.set/del; Use vim.defer_fn, Toast. libs/async.lua is CPU time-slicing, not process waiting, so it adds nothing.

Phases

Phase 1: Quick conditions risk: medium

Mergeable alone. Until Phase 2, a function that returns nothing counts as a no.

  1. Type and opts filter (core.lua): add cond to KeymapBase and to skip.
  2. Evaluate in safe_set (core.lua): once per call, before set/label. Early exit when opts.cond == nil. rhs = false deletion ignores cond.
  3. Quick path (cond.lua): boolean, or function under pcall; a thrown error is a no plus one toast.
  4. Tests (test-key-cond.lua): true/false/nil, quick true/false, error, multi-mode, deletion, no cond leaking into nvim_get_keymap.

Phase 2: Slow conditions risk: medium

Depends on Phase 1.

  1. Pending table: one token per key id and buffer; a new registration marks the old token stale. buffer = true/0 resolves to the current buffer at registration.
  2. Placeholder: function returned nothing and did not call done synchronously. Install via core.set with a toast rhs, expr/once stripped, desc kept. Label-only specs get no placeholder.
  3. Swap without a fake duplicate (core.lua): set(spec, buffer, site) reuses the registration-time call site in record_call.
  4. done(ok): idempotent, vim.scheduled. Stale token or invalid buffer: ignore. Yes: swap. Anything else: core.del, silent for a plain false.
  5. Timeout and errors: vim.defer_fn at 10 s (Cond.timeout_ms), one WARN toast then remove.
  6. Cancel on delete (core.del): late answer cannot revive a deleted key.
  7. Tests: placeholder exists, pressing toasts only, yes swaps with no conflict record, no is silent, error/timeout toast once, stale token, closed buffer, delete while pending, label-only, double done.

Phase 3: Callers risk: medium

Depends on Phase 2 (LSP rename is independent).

  1. Packer lazy keys (triggers/keys.lua): cond only on the temporary trigger; the real key set after plugin load is not re-gated.
  2. LSP rename (lsp/attach.lua): Beast.Lsp.KeySpec.cond becomes method; no users found in the repo.
  3. Codemap: add cond.lua under key/.

Phase 4: Refactor the GitHub keys risk: medium

Depends on Phase 3 step 1. A quick condition, so no placeholder is involved.

  1. Move the keys (lua/beast/init.lua): add <leader>ghp and <leader>ghi to the finder's packer.lazy keys with group = "GitHub" and a shared cond. Delete gh_keys, gh_root, gh_keys_set, sync_gh_keys and the BeastGithubKeys autocmd. Keep the cfg.git config block above them. The manual load_lib call goes away: the lazy trigger loads the finder.
  2. Behavior change, accepted: decided once at startup. Entering another remote's project later (:cd, another project's buffer) does not add or remove the keys until restart.
  3. Verify: start in a GitHub repo, a non-GitHub repo and a folder with no repo.

Testing Strategy

  • Headless: NVIM_APPNAME=BeastVim nvim --clean --headless -l tests/test-key-cond.lua (fake slow cond with vim.defer_fn, stubbed vim.system); also test-finder-keys.lua and test-finder-gh-keys.lua.
  • Phase 4 manual: start in a GitHub repo (keys listed under GitHub and working), a repo with another host or no remote (keys absent), and outside any repo (keys absent, no error). First press loads the finder.
  • Bench: scripts/bench-key-hint.lua (no new bench; no-cond path is one nil check).
  • Types: lua-language-server check from DEVELOPMENT.md.
  • Manual: PM scenarios 1-8 on a throwaway <leader> key, slow cond via vim.system({"sleep","3"}, {}, cb); timeout with sleep 60; :bwipeout before the answer.

Success Criteria

  • False or quick-false: key absent from hint, cheatsheet and Key.managed.
  • No cond or true: behaviour and conflict reporting unchanged.
  • Slow check: key exists immediately, startup unchanged, editor responsive.
  • Placeholder press toasts and runs nothing else.
  • Slow yes: real action runs, no new conflict record.
  • Slow no: removed silently. Error or timeout: removed with exactly one toast.
  • Buffer-local, replaced and deleted keys ignore a late answer.
  • cond never reaches vim.keymap.set.
  • packer.lazy keys honour cond.
  • GitHub keys exist exactly where the project has a GitHub remote at startup; sync_gh_keys and its autocmd are gone.
  • New test passes, existing key/finder key tests pass, type check clean.

Decisions for you

1. LSP cond field recommended: rename to method
Alternative: keep it and override the type on Beast.Lsp.KeySpec, leaving two meanings of cond on one spec family.
2. Packer lazy keys in this change recommended: include (Phase 3 step 1)
Alternative: ship only Key.safe_set and let packer.lazy ignore cond until a follow-up.
