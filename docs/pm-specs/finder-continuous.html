Continuous finder

Press one key on a result list to open a follow-up picker that only looks inside what you just found. Files, buffers or help pages then grep in those; a pull request then the files it changed (each with its diff), then grep in those. Backspace steps back to the earlier picker exactly as you left it.

Problem

You find a set of files, then want to search inside only those. Today you close the picker, open grep, and grep searches the whole project, so the narrowing is thrown away. Same with pull requests: to see what a PR changed you leave the editor, and coming back to the PR list loses your search.

Why now: the finder already has a prompt, list, preview and both local and GitHub pickers. A follow-up picker is the natural next step, and the GitHub pickers just shipped.

Target behavior

Try it (demo data, click the box, then type)

Keys: type to filter, <C-g> deeper, <BS> on an empty prompt or <C-o> back, <C-j>/<C-k> or arrows to move, <Esc> closes the chain. Rows and counts are fake; the behavior is what the spec describes. Try: Files, type "finder", C-g, type "preview", BS, BS.

  • Key hints are dim tooltip-like text on a line just below the picker's bottom border, right-aligned to its right edge (outside the frame, never a list row): the key that goes deeper (only with a next step) and, below level 1, the key that goes back, naming the destination. Hidden when there is no room below.
  • Title reads "scope › this picker": "38 Files › Live Grep", "PR <title> › Files Changed (5)". A long PR title is cut with ....
  • Rows use the Live grep list look: file name plus dim parent folder; in Grep the matching lines sit indented under their file with line:col.
  • PR level 2 is only the changed file paths; the diff and +/- counts are in the preview.
  • Diff preview: added lines green, removed red, hunk headers dim.

Behavior rules

  • One key goes deeper: <C-g>, meaning "continue inside what I see".
    • Files, Buffers, Help and a PR's changed files -> grep inside the files currently matching (Help: the help pages of the matching tags).
    • Pull Requests -> the files changed by the highlighted PR.
    • Issues -> grep inside the text (title and description) of the listed issues. Issues are not files, so this is the closest meaning of "grep" there.
    • Pickers with no next step (Live Grep itself) show no hint.
  • Grep reads files on disk in your working tree. Buffers with no file, files deleted by a PR and files missing locally are left out; the title count reflects what is left.
  • Scope for Files = everything that currently matches (not only the highlighted row); empty prompt = whole file list. For PRs = the highlighted PR.
  • Files and Buffers rows use the grep file look (icon, name, dim folder) everywhere, chain or not. The buffer number is no longer shown in the row.
  • A follow-up picker always starts with an empty prompt.
  • Back is a stack, not a history. <BS> on an empty prompt, or <C-o> any time, goes one level up. Going deeper again starts fresh.
  • Going back restores prompt text, results and highlighted row. GitHub lists are not searched again; file lists are re-run (cheap) and the row is restored by name.
  • <Esc> / <C-c> close the whole chain. <Enter>, <C-s>, <C-v> act on the result and close it. <C-y> copies path (URL for PRs) at any level.
  • Depth is not limited. Today's longest chain has three levels (PR > Files Changed > Live Grep).
  • No partial scope: <C-g> while results are still being collected gives a toast.
  • Title and hint below the picker always show the chain and where <BS> goes.
  • Level 2 can fail alone, in-list, and <BS> still works.

Decisions for you

Deeper key. <C-g> ("go"). It is free in the finder and works in insert and normal mode of the prompt. Recommended
Alternatives: <C-o> deeper and <C-i> back (collides with Tab in terminals), or a per-picker key (more to remember).
Back key. <BS> on an empty prompt, plus <C-o> that always works (because GitHub-style prompts are rarely empty, and level 2 prompts you typed into need a way out without clearing). Recommended
PR level 2 shows only the changed file paths; the diff lives in the preview (your request). Searching inside the diff text can be a later level. Recommended
Enter on a changed file opens its diff in a read-only buffer (the local file may be a different version than the PR). Recommended
Esc closes the whole chain (not one level), so Esc always means "I am done". Recommended

Success criteria

  • Files, Buffers, Help <C-g>: grep only returns matches inside the files (or help pages) that matched the prompt.
  • In Issues, <C-g> greps title and description of the listed issues, matches shown under each issue.
  • From a PR's changed files, <C-g> greps the local copies; deleted or missing ones are left out and the title count says how many remain.
  • Pull Requests <C-g>: files changed by the highlighted PR (paths only), diff with status and +/- counts in the preview; typing filters by path.
  • <BS> on empty prompt and <C-o> restore the earlier prompt, results and highlighted row.
  • Going back to the PR list makes no GitHub search.
  • <Esc> closes the whole chain; <Enter> on a result closes it too.
  • Title shows the chain; hint shows <C-g> only with a next step and <BS> only below level 1.
  • <C-g> with no next step, an empty list, or a still-scanning list shows a toast and changes nothing.
  • Failed or huge changed-files listings are handled in-list.
  • Files and Buffers rows show icon, file name and dim folder (STATE 0); Buffers still marks modified buffers with [+].
  • Files and Buffers rows show icon, file name and dim folder (STATE 0); Buffers still marks modified buffers with [+].
  • Apart from that row look, a picker opened normally looks and behaves exactly as before.

Out of scope

  • Forward navigation / full history (browser-style).
  • More chains (Grep -> files with matches, Issues -> linked PRs, PR -> grep inside the diff text, LSP references -> grep).
  • Hand-picking several rows as a scope.
  • Whole-PR diff as one document, reviewing or commenting.
  • GitLab, deferred.
