Browse GitHub PRs and issues in the finder

Two new pickers, one for pull requests and one for issues. The prompt is a real GitHub search query (is:pr state:open by default) that you can edit freely, so one key per kind covers open, closed, merged, mine, another repo, and anything else GitHub can search.

Icons here are plain symbols; the real UI uses Nerd Font git icons. Repo and PR names are illustrative.

Problem

To skim a repo's PRs and issues you leave the editor, open a browser, find the right tab and type filters into GitHub's search box. A separate key per view (open PRs, all PRs, my PRs ...) only multiplies key bindings and still cannot express a view nobody planned for.

Why now: the finder already has a prompt, list, preview and live sources that re-run as you type. GitHub's search syntax is already known to you and is more powerful than any fixed set of views.

Scenarios

1 - Skim open pull requests (happy path) 
Step 1: Press <leader>ghp inside a repo that has a GitHub remote.
  Picker opens with "is:pr state:open " in the prompt, cursor at the end.
  The list fills with the repo's open PRs, newest first.

Step 2: Press Down / Up (or Ctrl-n / Ctrl-p).
  The preview follows. Title, state, author, labels appear at once;
  description and conversation fill in a moment later.

Step 3: Go back to a PR already visited.
  Its preview appears instantly (not fetched again while the picker is open).
2 - Closed or merged work by editing the text 
Step 1: Change "state:open" to "is:merged".
  Prompt: "is:pr is:merged". Spinner briefly, then merged PRs only.

Step 2: Append "author:@me".
  Only merged PRs authored by you remain.

No separate key, no extra menu: the text is the filter.
3 - Words and qualifiers together 
Step 1: Type " hub" after the default text.
  Open PRs where GitHub finds "hub" (title, description, comments).

Step 2: Type " label:bug".
  The list narrows further.

Words are matched by GitHub like the github.com search box, not by the finder's fuzzy matcher.
4 - Switch from PRs to issues without closing 
Step 1: Replace "is:pr" with "is:issue".
  Prompt: "is:issue state:open". The list becomes issues;
  icons and preview switch to the issue style.
5 - Look at another repo 
Step 1: Type "repo:neovim/neovim is:issue label:bug".
  Bug issues of that repo are listed; title bar reads "Issues - neovim/neovim".

Without repo:, org: or user:, the search is always limited to the current repo.
6 - Open or copy the highlighted item 
Step 1: Press Enter on a row.
  Picker closes; the PR or issue opens in the default browser.

Step 2 (alternative): Press Ctrl-y.
  URL is copied, picker stays open, a toast confirms.
7 - Typing fast, slow network 
Step 1: Type "fix" quickly, then keep typing "ing the bug".
  One search starts, after you pause (a little longer than for local pickers).
  If an older, slower search finishes after a newer one, its results are thrown away.
  The list always matches the text currently in the prompt.
8 - Cannot run (errors and edge cases) 
A: <leader>ghp in a folder that is not a GitHub repo.
   Picker does not open. Toast: "No GitHub remote found for this directory".

B: "gh" not installed or not logged in.
   Picker does not open. Toast says what is missing and how to fix it
   ("GitHub CLI (gh) is not installed" / "Run `gh auth login` first").

C: Half-written or unknown qualifier ("is:pr state:", "foo:bar").
   GitHub does not reject these, it finds nothing: "No results for this search" (D).
   Finishing the qualifier brings results back on its own.

C2: The search really fails (repo not found or no access, rate limit, network, login expired).
   One-line reason in the list (STATE 5), no popup. A rate limit says when it resets.

D: Valid search, nothing found.
   "No results for this search", count 0/0.

E: More than 100 matches.
   Newest 100 shown, count reads "100+" so you know to narrow the query.
9 - Cancel 
Step 1: Esc (normal mode) or Ctrl-c at any time.
  Picker closes. Nothing opened or copied. A running search is dropped.

Behavior rules

  • The prompt text goes to GitHub as-is, never fuzzy-filtered locally.
  • Defaults: is:pr state:open and is:issue state:open (trailing space). Only a starting point; any of it can be deleted.
  • The text decides the kind. With no is:pr / is:issue left, PRs and issues show together, told apart by icon.
  • Limited to the current repo unless the text has repo:, org: or user:.
  • Newest created first, like GitHub's own PR and issue pages, unless the text has its own sort: (e.g. sort:updated-desc).
  • At most 100 results, no paging.
  • A search starts only after typing pauses. Old list stays with a spinner meanwhile. Out-of-date answers never overwrite newer ones.
  • GitHub errors and empty results appear inside the list. Only "cannot start" problems (no remote, no gh, not logged in) use a toast.
  • Preview shows list-level info instantly, then description and conversation. Fetched previews are kept until the picker closes. Read-only, scrolls like other previews.
  • Reopening starts from the default text, not the last query.
  • Enter opens in browser, Ctrl-y copies URL, Ctrl-s / Ctrl-v do nothing. <leader>ghp = PRs, <leader>ghi = issues (<leader>gp is already "Preview hunk").
  • Icon colors: open green, draft grey, merged purple, closed red. Issues closed as "not planned" are grey, others purple.

Decisions for you

Items 1, 2 and 4 are confirmed. Item 3 is still a recommendation.

1. Keys confirmed
  • <leader>ghp / <leader>ghi. No clash, grouped as "GitHub". Both keys stay even though the text can switch kind: opening straight on the wanted kind is the common case.
2. Deleting is:pr / is:issue confirmed
  • Show both kinds together. The text is the single source of truth.
3. Enter
  • Open in the browser recommended for v1.
  • Open an in-editor read-only page for the item.
4. Default order confirmed
  • Like GitHub browsing: newest created first. Add sort: to change it.

Success criteria

  • The two keys open pickers whose prompt holds is:pr state:open / is:issue state:open , cursor at the end.
  • The list shows the current repo's open items with state icon, number, title, author, colored labels.
  • Editing the text (state, author, label, words, other repo, is:pr to is:issue) matches what github.com shows for that text.
  • The preview shows metadata, description and conversation; revisiting an item is instant.
  • Fast typing yields one search; the list never shows results for older text.
  • While searching, the old list stays and a spinner replaces the count.
  • Failed searches (repo not found, rate limit, network) and empty results show one in-list line, not a popup. Unknown qualifiers simply give no results.
  • No remote / no gh / not logged in gives a clear toast and no empty picker.
  • Enter opens the browser, Ctrl-y copies the URL, Esc closes with no side effects.
  • Look and keys match the existing finder pickers.

Out of scope

  • Write actions: comment, close, merge, label, assign, react. v1 is for scanning.
  • Checking out a PR branch and viewing its diff in the editor. Natural follow-up.
  • An in-editor page for a PR or issue.
  • Highlighting or completing qualifiers (state:, label: ...) in the prompt.
  • Paging beyond 100 results.
  • Remembering the last query between openings.
  • Opening outside a GitHub repo to search by repo: only.
  • GitLab (planned as a follow-up, own spec). Its filtering differs: UI filter tokens, the GLQL query language, and glab flags, so it is not a copy of the GitHub query box.
  • Other forges (Bitbucket, Gitea).
