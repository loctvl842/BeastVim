Big file mode

When you open a very large file (say a 7 MB, 120,000-line XML export) the editor switches off the costly features for that file only. You get one short notice, the file stays readable and editable, and every other file keeps everything.

Sample: realistic_orders_120k.xml, 7.4 MB, 121,112 lines.

Problem

Opening a huge file feels broken today: the cursor stutters, scrolling lags, and typing a character can freeze the editor. It does the same rich work as for a 50-line file (grammar coloring, symbol trail, git marks, a language server) on 120,000 lines, and every keypress pays for it.

Today the only protection is a cap on bracket matching. You cannot tell if the lag means "big file" or "something is wrong".

Why now: logs, data exports, generated code and minified bundles are normal work. The editor should open them without a fight, and say plainly that it simplified itself.

Target behavior

State 1 - opening the sample file

┌───────────────────────────────────────────────────────────────────────┐
│                                       ┌───────────────────────────┐   │
│                                       │ Big File                  │   │
│                                       │ realistic_orders_120k.xml │   │
│                                       │ (7.4 MB) is large. Some   │   │
│                                       │ features are disabled.    │   │
│                                       └───────────────────────────┘   │
│   1  <?xml version="1.0" encoding="UTF-8"?>                           │
│   2  <!-- Synthetic deeply-nested commerce export fixture. -->        │
│   3  <commerceExport xmlns="urn:example:commerce:orders:v3" ...>      │
│   4    <orders>                                                       │
│   5      <order id="ORD-0000001" status="backordered" ...>            │
│  ...                                                                  │
│ NORMAL  realistic_orders_120k.xml            Ln 1, Col 1  XML  UTF-8  │
└───────────────────────────────────────────────────────────────────────┘
  • One notice on open, naming the file and its size.
  • Line numbers stay. The statusline still says XML.
  • Text is still colored (simple, fast coloring), just not grammar-aware.

State 2 - what stays on, what is switched off (this file only)

Stays on
  • line numbers
  • simple (regex) coloring
  • indent guides and scope highlight
  • search, search count, replace
  • editing, undo, copy/paste
  • autopairs
  • statusline, tabline
  • file explorer, finder
Switched off
  • grammar-aware coloring (treesitter)
  • smart indent from grammar
  • sticky "enclosing scope" header
  • symbol trail in the winbar
  • language server (no LSP attach)
  • git change marks and inline blame
  • smooth-scroll animation
  • bracket-pair highlight (matchparen)
  • grammar folding (manual only)
  • concealed text
  • extra signs and fold marks in the gutter

State 3 - a normal file next to it

┌─────────────────────────────┬─────────────────────────────┐
│ big.xml  (big file)         │ init.lua  (normal)          │
│  1  <?xml ...?>             │  1  local M = {}            │
│  2  <orders>                │  2  function M.setup()      │
│ guides, no git marks        │ │   guides, git marks, LSP  │
└─────────────────────────────┴─────────────────────────────┘

Decided per file. A big file never changes any other file.

Scenarios

1 - Open a big file (happy path)

Step 1
Run nvim realistic_orders_120k.xml. The file appears with a "Big File" notice showing name and size.
Step 2
Press j / k, Ctrl-D / Ctrl-U, G, gg, 50000G. Cursor and view move immediately.
Step 3
Type a character mid-file. It appears at once; nothing freezes.
Step 4
Search /ORD-0099999 then n. Match found, highlighted, count shown as usual.

2 - Open a normal file

Step 1
Open lua/beast/option.lua (a few KB). No notice, every feature as before.

3 - Minified file: small but extremely long lines

Step 1
Open app.min.js (900 KB, 3 lines, average line over 1,000 characters). The notice appears even though the size is under the limit; the long lines are the cost, so the same features go off.

4 - Big file and normal file side by side

Step 1
:vsplit init.lua from the big file. Right window keeps all features; left stays simplified.
Step 2
Move between windows. Each keeps its own behavior, nothing leaks.

5 - Open the same big file again later

Step 1
Close the buffer, open it again. The notice shows again, once for that open.
Step 2
Re-enter the same open buffer from another window or :b. No new notice.

6 - Edge: new or empty file

Step 1
nvim new_file.xml (not on disk) or an empty file is treated as normal. No notice.

7 - Edge: file grows large while editing

Step 1
A 200 KB file is open and you paste in 10 MB. Nothing changes mid-session; the decision is made on open. Reopen and it is treated as big.

Behavior rules

  • Big means either: size on disk over 1.5 MB, or average line length over 1,000 characters (looks minified). Both limits are configurable.
  • Decided per buffer, once, when the file opens. Later edits do not flip it.
  • Only that buffer is affected.
  • The file type is not changed (XML still says XML), so tabs and comment settings still apply.
  • Exactly one notice per open: a toast naming the file and its size in KB / MB. Can be turned off in configuration; features are still switched off.
  • Search, search count, editing, undo, registers, indent guides, explorer and finder are never switched off.
  • Indent guides and the scope highlight stay on, but only look at a limited stretch around the cursor, so they stay cheap on a huge file.
  • The list of switched-off features is configurable, to keep one on at your own cost.
  • Switched-off features stay off for the buffer's whole life, including :e, reload from disk and re-attach events.
  • Files that cannot be measured (new, empty, unreadable) are normal.
  • Non-file buffers (help, finder, explorer, terminal, scratch) are never big.

Success criteria

  • Opening realistic_orders_120k.xml shows exactly one "Big File" notice with name and size.
  • In that file, holding j, Ctrl-D and G feels instant; typing shows immediately.
  • None of the switched-off features run in that buffer (no LSP, no treesitter coloring, no git marks, no symbol trail, no sticky header).
  • Line numbers, simple coloring, search, search count, undo and statusline still work.
  • A minified 900 KB file triggers the same behavior.
  • A small file opened in the same session keeps every feature.
  • Big and normal files in split windows each keep their own behavior.
  • The file type of a big file is still shown (XML for the sample).
  • Turning the notice off silences it without re-enabling features.
  • Reopening the same big file shows the notice again once per open.

Out of scope

  • A command or key to switch features back on for one big file. Deferred until the need is real.
  • Re-evaluating a buffer that grows past the limit mid-session.
  • A "BIG" indicator in the statusline. The notice is enough for v1.
  • Special handling of big files in the finder preview or explorer.
  • Streaming or partial loading. The whole file is still loaded.
  • Opening binary files differently.
