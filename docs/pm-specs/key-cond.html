Keymap condition

A keymap can carry a cond. When it is false the keymap does not exist. For a slow check (an external command) the keymap is registered right away as a placeholder: pressing it only shows a "still checking" toast. A yes turns it into the real keymap; a no, an error or a timeout removes it and tells you why. The editor never waits.

Problem

Some keymaps only make sense in some situations ("only if gh is installed"). Today you either register them always, which leaves a dead key in the hint, or you wrap them in a hand-written if. When that check needs an external command, the simple way is to wait for it, which blocks startup.

Why now

The external-command case exposes the gap: without a condition that can wait without blocking, every such keymap costs startup time or leaves a dead key.

Target Behavior

STATE 1 — Condition is true (or a quick check answers true):
┌─ <leader> ───────────────┐
│  f   Files               │
│  g   Git                 │
│  gp  Pull requests       │   <- real keymap
└──────────────────────────┘
STATE 2 — Condition is false (boolean or quick check):
┌─ <leader> ───────────────┐
│  f   Files               │
│  g   Git                 │
└──────────────────────────┘   <- no "gp": not in hint, not in cheatsheet
STATE 3 — Slow check running: listed as a placeholder, pressing it only toasts:
┌─ <leader> ───────────────┐
│  f   Files               │
│  g   Git                 │
│  gp  Pull requests       │   <- placeholder
└──────────────────────────┘
                     ┌────────────────────────────────┐
  press <leader>gp:  │ Pull requests: still checking  │
                     │ (is `gh` available?)           │
                     └────────────────────────────────┘
STATE 4 — Slow check answers yes:
The placeholder silently becomes the real keymap. <leader>gp now runs it.
STATE 5 — Slow check answers no, fails, or times out:
┌────────────────────────────────────────────┐
│ <leader>gp disabled: check timed out (10s) │   <- notification
└────────────────────────────────────────────┘
┌─ <leader> ───────────────┐
│  f   Files               │
│  g   Git                 │
└──────────────────────────┘   <- placeholder gone
cond = true                           -- boolean: fixed answer, no placeholder
cond = function() ... return ok end   -- quick check: answers right away, no placeholder
cond = function(done) ... done(ok) end
                                      -- slow check: placeholder until done(ok) is called

A function that returns true/false is quick. A function that returns nothing and calls done later is slow.

Scenarios

1 — Boolean condition 
Step 1: cond = false  -> not registered; absent from hint and cheatsheet.
Step 2: cond = true, or no cond  -> behaves exactly as today.
2 — Quick function condition 
Step 1: cond = function() return vim.fn.executable("gh") == 1 end, called once at registration.
Step 2: returns true  -> registered at once as the real keymap.
Step 3: returns false -> not registered.
3 — Slow condition, external command (happy path) 
Step 1: Neovim starts. The keymap is registered at once as a placeholder. Startup does not wait.
Step 2: The command runs in the background. The user works as normal; <leader>gp is listed in the hint.
Step 3: The command answers yes. The placeholder silently becomes the real keymap.
4 — Pressing the placeholder while the check runs 
Step 1: The user presses <leader>gp too early. A toast says it is still being checked. Nothing else happens.
Step 2: Pressed again: same toast (stacks as "x2"). The press is not remembered; the action does not run on its own after a yes.
5 — Slow condition answers no 
Step 1: The placeholder is removed, gone from hint and cheatsheet. No notification: "no" is the intended outcome.
6 — Slow condition fails or hangs 
Step 1: Command missing, exits with an error, or the condition raises.
  Treated as no. Placeholder removed, notification names the keymap and the reason.
Step 2: The command never ends. After 10 seconds the check is abandoned, placeholder removed, notification says it timed out.
7 — Buffer-local keymap 
Step 1: buffer = true + slow cond for buffer 7: a placeholder in buffer 7 only.
Step 2: Same spec attached to buffer 9: checked again, own placeholder and own answer.
Step 3: Buffer 7 closes mid-check: the late answer is thrown away, no error, no notification.
8 — Deleted or replaced while its check runs 
Step 1: Placeholder pending, author deletes the keymap. Removed as today; the late yes does not bring it back.
Step 2: Placeholder pending, a newer registration of the same keys replaces it. The older answer is thrown away.

Behavior Rules

  • cond is optional. No cond means exactly today's behavior.
  • A boolean or quick function answers at once. A "no" means never registered: not in the hint, cheatsheet or conflict check.
  • Only a slow check creates a placeholder.
  • A placeholder is a real entry for hint, cheatsheet and conflict checks, with the keymap's description. Pressing it only shows a toast, whatever the real action was.
  • Yes: placeholder becomes the real keymap. No, error or timeout: placeholder removed.
  • A plain "no" is silent. An error or timeout notifies, once per keymap.
  • Checked once per registration (once per buffer for buffer-local keymaps). No live re-checking.
  • A slow function answers by calling done; a quick one by returning. Never both.
  • Anything other than a clear yes is a no: nil, an error, a timeout, a failed command.
  • The editor never blocks: no startup delay, no frozen input. Slow answers are abandoned after 10 seconds.
  • Late answers for a deleted, replaced, or closed-buffer keymap are thrown away.
  • Pressing a placeholder never queues the action for later.
  • cond is not passed to Neovim as a key option.
  • Label-only entries (group names) can carry cond; with no action to block they get no placeholder and are listed once the check says yes.

Success Criteria

  • cond = false, or a quick false, is absent from hint and cheatsheet.
  • cond = true or no cond is unchanged.
  • A slow-check keymap exists right after registration, with no added startup time.
  • Pressing a pending placeholder toasts "still checking" and does nothing else.
  • After a slow yes the same keys run the real action, no restart.
  • After a slow no the keymap disappears from hint and cheatsheet without a notification.
  • After an error or timeout it disappears and one notification explains why.
  • The editor stays responsive while a slow check runs.
  • Buffer-local keymaps are checked per buffer; a closed buffer's late answer is ignored.
  • Deleting or replacing a keymap mid-check is not undone by the late answer.

Decisions for you

1. Notification on a plain "no" proposed: silent
"No" is the intended outcome (e.g. gh simply not installed). Alternative: always notify when a placeholder is removed. Your note asked for a notification on timeout, so error and timeout notify.
2. Timeout proposed: 10 s
Shorter loses keymaps on a slow machine; longer keeps the placeholder longer.
3. Placeholder in the hint proposed: listed like any keymap
Alternative: dimmed with a "checking" tag. More honest, adds a visual state.

Out of Scope

  • Re-checking later (folder changes, tool installed after startup). One check per registration keeps it predictable; a reload re-checks.
  • Running the action automatically after a late yes. Surprising to run something pressed seconds ago.
  • Sharing one command's answer between many keymaps. Authors can compute it once in their own config.
  • cond deciding when to delete a keymap. Deletion stays explicit.
