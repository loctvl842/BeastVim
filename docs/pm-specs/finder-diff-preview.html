Finder diff preview

Highlight a file in Files Changed (of a pull request or a commit) and the right side shows its diff the way GitHub does: line numbers, whole red and green lines, the exact changed words emphasized, long lines wrapped. Reviewing a change no longer needs the browser.

Scenarios

1 - Happy path: review a pull request file by file

Step 1<leader>ghp, move to a PR, <C-g>. Title "PR Refactor m4 › Files Changed (5)"; the first file's diff fills the right side as in STATE 1.
Step 2<Down>: the next file's diff replaces it, starting at the top, no flicker.
Step 3Scroll the preview with the usual keys. Numbers, marks and text move together; a wrapped line is never half off screen.
Step 4<Enter> on a file: unchanged, the diff opens in a read-only buffer.

2 - A long line

It wraps onto the next rows; wrapped rows have empty number columns and the same red or green, so it reads as one line. Nothing is cut at the edge. Resizing the terminal re-wraps.

3 - An edited line: which words changed

Similar removed and added lines: stronger red and green on the differing words. Lines that share little, or pure additions or deletions: soft color only.

4 - Several changed places in one file

Between changes a muted row says "13 unchanged lines", then the change's own header (lines and nearest function or heading). If the first change is not at the top, "19 unchanged lines above". Numbers stay right across the gap (23, 24, 25, 26, then 40).

5 - Added, deleted and renamed files

Added: only the new-line column, all green, "added +42 -0". Deleted: only the old-line column, all red, "removed +0 -18". Renamed: "renamed" and "(was <old path>)".

6 - No diff to show

Binary, image, or too large for GitHub: file name, status and "(diff too large or binary)". No rows, no error.

7 - The commits of a PR use the same look

Highlight a commit: its message, file list, then each file's diff drawn as in STATE 1. <C-g> to that commit's Files Changed gives the same preview as scenario 1.

8 - Changing the colorscheme

Red, green, stronger shades and number columns follow the new colorscheme, dark and light. The finder keeps its own colors while open, as for everything else.

9 - Moving fast and going back

Holding <Down> across many files stays smooth; only the file you stop on is drawn. <BS> on an empty prompt or <C-o> goes back a level, and the previous level's diff shows again for the same row.

Behavior rules

  • Applies to Files Changed (PR and commit) and to the per-file diffs inside a commit's preview.
  • Unified view, one column, top to bottom. No side-by-side.
  • Number columns are as wide as the largest line number in the file, so rows stay aligned.
  • Raw @@ ... @@ text is never in the body; each hunk is one muted row.
  • The small bar in the header is proportional to additions vs deletions.
  • Marks and numbers are not part of the text: copying from the preview takes only the code.
  • "No newline at end of file" is shown as a muted note.
  • Only the lines GitHub returns exist; hidden lines cannot be expanded here.
  • All colors come from the colorscheme.
  • <Enter> keeps opening the raw diff buffer; this spec does not change it.

Decisions for you

1. Long lines

Recommended Wrap (like GitHub).
Alternative Keep cutting and scroll sideways.

2. Code coloring

Recommended Color the code for the file's language (keywords, strings) on top of red/green.
Alternative Plain text on red/green: simpler, faster.

3. Commit preview

Recommended Same look for the diffs inside a commit's preview, so the whole chain is consistent.
Alternative Only the Files Changed level.

4. Enter

Recommended Unchanged: raw diff in a read-only buffer (easy to copy and search).
Alternative Open the same drawn diff in a full window.

Success criteria

  • Highlighting a file shows the header (status, +N -M, bar) and the diff with old and new line numbers.
  • Removed lines are red and added lines green across the whole row; context is neutral.
  • On an edited line, only the changed words get the stronger shade.
  • A long line wraps with empty number columns and keeps its color; nothing is cut at the edge.
  • Gaps show "N unchanged lines"; numbers stay correct across them.
  • Added, deleted, renamed, binary and too-large files render as in STATES 3 and 4.
  • A commit's preview draws each file's diff in the same style.
  • Changing the colorscheme recolors the diff correctly, dark and light.
  • Moving through files is as fast as before; the diff always starts at the top.
  • <Enter>, <BS>, <C-o> and <C-g> behave exactly as before.

Out of scope

  • Side-by-side view: the preview is half the screen wide.
  • Expanding hidden unchanged lines: needs the full file at that commit; deferred.
  • Review features: comments, "Viewed" checkmarks, approving, suggestions.
  • Toggling the changed-word emphasis off; it is always on, as in the git preview.
  • Diffs of local changes (git hunk preview), which already has its own look.
